# SaleScope AI 项目上下文

这份文件是当前会话的压缩上下文，用来在后续继续开发、调试或面试前快速恢复项目状态。

## 当前定位

SaleScope AI 是一个面向销售和运营人员的销售数据分析 Agent 工作台。

核心原则：

- 大模型负责理解问题、选择分析方法、澄清缺失信息、生成 JSON 查询计划。
- 本地程序负责读取真实数据、执行计算、校验结果、生成图表。
- 模型不直接编造数字。
- 页面固定展示答案、依据、步骤和错误原因。

## 当前技术架构

```text
React + Vite 前端
        ↓
用户自然语言问题 + 最近 10 条对话历史
        ↓
Wanqing 大模型
        ↓
JSON 查询计划 / 澄清请求
        ↓
本地分析执行器
        ↓
真实 CSV 数据计算
        ↓
页面展示结果
        ↓
SVG 图表写入 charts/
```

## 环境配置

运行前需要配置 `.env`：

```env
WQ_API_KEY=你的万擎API密钥
WQ_MODEL_ID=你的端点模型ID
WQ_BASE_URL=https://wanqing-api.corp.kuaishou.com/api/gateway/v1/endpoints
WQ_API_PATH=/chat/completions
WQ_TIMEOUT_MS=30000
WQ_DEMO_FALLBACK=true
```

注意：

- 不要把 API Key 写进源码、README 或前端产物。
- `.env` 已被 `.gitignore` 忽略。
- 当前对话中曾公开过旧 API Key，正式演示前建议到 Wanqing 控制台撤销并重新生成。
- 如果 Wanqing 不可用，`WQ_DEMO_FALLBACK=true` 会让系统进入本地演示模式，不会崩溃。

## 迭代历史

### 第一阶段：产品原型

目标：先跑通销售分析工作台。

完成内容：

- React + Vite 项目初始化。
- 企业亮色数据看板风格。
- 总览页包含 KPI、月度趋势、地区分布、产品排行。
- 上传入口和数据源状态反馈。
- 原始 AI 洞察区域为演示文案，尚未接真实模型。

### 第二阶段：自动检查

目标：确保项目不是只能看，而是可以被检查。

完成内容：

- 增加 `npm run check`。
- 实际读取并解析 `data/sales-data.csv`。
- 检查必需字段、行数、日期、金额、折扣、数量、重复记录。
- 校验总销售额、总数量、最高地区、最高产品。
- 检查上传、下载、错误处理和无限循环风险。

### 第三阶段：真实数据计算

目标：从“演示原型”升级为“真实计算”。

完成内容：

- 浏览器和服务端共用 `src/dataAnalysis.js`。
- 支持 CSV 真实解析。
- 支持总营收、最高地区、前三产品等基础问题。
- 结果来自当前数据计算，不是写死答案。
- 页面展示计算过程、结果依据和错误原因。

### 第四阶段：接入 Wanqing

目标：让模型负责理解自然语言，不负责直接算数。

关键决策：

- 模型输出 JSON 查询计划。
- 本地程序校验并执行计划。
- 不允许模型直接生成答案数字。

重要修正：

- 最初使用公网 Wanqing 地址时返回 `403 AccessKey IS UNAVAILABLE`。
- 根据官方办公网示例，改用：

```text
https://wanqing-api.corp.kuaishou.com/api/gateway/v1/endpoints
```

- 之后 Wanqing 调用返回 `HTTP 200`，真实模型链路打通。

### 第五阶段：Agent 循环

目标：让产品从“单次问答”升级为“分步分析”。

完成内容：

- Agent 最多尝试 3 次。
- 每次失败保留错误原因。
- 根据错误自动修正查询计划。
- 展示“理解问题 → 尝试计算 → 检查结果 → 给出答案”。
- 万擎不可用时自动进入演示模式。

### 第六阶段：多轮对话与澄清

目标：提升模型自主性，同时保持计算安全。

完成内容：

- 前端保存最近 10 条 `user` / `assistant` 消息。
- 服务端把历史消息传给 Wanqing。
- 模型可以理解“按地区看”“再比较一下”等上下文追问。
- 模型可以返回两种结果：
  - `plan`：生成查询计划；
  - `clarify`：信息不足时先追问。
- 问题模糊时模型会主动澄清，不猜数字。

### 第七阶段：画图能力

目标：让用户可以直接要求生成图片。

完成内容：

- 支持柱状图、折线图、地区对比图。
- 支持按月 × 地区收入占比的多系列折线图。
- 服务端把 SVG 图片保存到 `charts/`。
- 图片通过 `/charts/*` 访问。
- 最终答案包含图片保存路径。
- 分析报告页展示图片、路径和文件大小。
- 第一次画图失败时可以自动切换图表类型重试。

### 第八阶段：自动评测

目标：证明产品可以被持续验证，而不是只能回答几个演示问题。

完成内容：

- 新增“自动评测”页面。
- 定义 10 道题，覆盖：
  - 总数计算；
  - 最高/最低；
  - 地区比较；
  - 产品比较；
  - 月份分析；
  - 客户类型；

  - 利润分析；
  - 筛选条件；
  - 画图。
- 逐题调用分析接口。
- 自动判断真实答案或图片结果。
- 展示通过/失败、实际输出、错误原因、总分和准确率。
- 保存完整结果到 `evaluations/latest.json`。

## 重要边界

- 当前基础版只支持 CSV，不支持 Excel 二进制文件。
- 图表当前是 SVG，不是 PNG。
- 模型只能生成查询计划，不能直接修改文件或执行任意代码。
- 本地计算操作是白名单制的。
- 当前数据量适合演示和中小规模分析，大数据需要后端任务和数据库。
- Wanqing 不可用时会进入演示模式，页面仍然可运行，但不是真实模型模式。

## 第十阶段：ReAct 工具循环（2026-10-29）

- 用户目标：模型能组合工具处理没预设过的问法，例如每个月各地区收入的堆积柱状图。
- 新增 `server/agentLoop.js`，通过 OpenAI 兼容 messages 传递 JSON action 和 Observation，无需模型原生 function calling。
- 工具：inspect_data（样例/分类/年份）、query_data（真实查询）、render_chart（保存 SVG）、finish（引用结果）、clarify（必要澄清）。每个工具结果继续送入同一次模型上下文，支持多次查询与绘图，JSON 和执行错误都可继续修正。
- 默认最多 8 轮、总时限 180 秒，单次模型请求继续读取 WQ_TIMEOUT_MS。模型连接异常仍标记 demo 或报错，不冒充 wanqing。
- 二维分组支持月份/地区/产品/类别/客户类型的两两组合，执行求和、平均、组内占比；年月标签防止跨年合并，缺失组合补零，无记录月份不推断为零收入。
- 新增 stacked-bar 图形，模型选择图表类型，严格图表失败交由模型修正；普通关键词不再把明确的柱状图覆盖为月度折线。
- finish 引用 result_id 和对应 chart_id，最终数字使用本地结果；用户要求的堆积图、占比、年份和完整月度维度会做校验。
- 页面支持系列结果文本、堆积图快捷问题和窄屏图表横向滚动。没有新增完整聊天记录界面。
- 新增 `npm test` 行为测试。以前的 101 项结构检查和 10 题评测不能充分证明所有自主任务正确；本次新增回归测试覆盖数据、工具 Observation、错误修正与结束校验。
- 能力仍受工具边界限制；ReAct 不意味着任意代码执行或自动预测。后续扩展新问题应增加通用工具与行为测试，而不是增加问句模板。
- 实测月度地区金额堆积图和连续追问占比堆积图均 source=wanqing，query_data → render_chart → finish 共 3 轮。金额合计 57,100，占比每月合计 100%，图片 GET 返回 200。
- 批量回归发现万擎 RPM 限制（HTTP 429），新增按服务端提示等待重试：最多 2 次、单次最多 60 秒，计入总时限，步骤保留限流原因。
- 设计验证：独立 Chrome 实际渲染金额堆积 SVG，标题、图例、年月和各段金额可见，无重叠；页面初始渲染正常。MyFlicker 浏览器原生交互/截图遇到超时与捕获占用，因此未据此宣称分析报告页交互全量通过。

## 面试主叙事

这个项目的核心不是“接一个大模型聊天框”，而是把以下能力串成闭环：

```text
自然语言理解
→ 查询计划生成
→ 真实数据计算
→ 结果校验
→ 错误修正
→ 图表生成
→ 自动评测
```

一句话总结：

> 我做了一个销售数据分析 Agent。它不是让大模型直接猜答案，而是让大模型理解问题，本地程序执行真实计算，所以答案可解释、可验证，也能通过自动评测持续检查质量。
